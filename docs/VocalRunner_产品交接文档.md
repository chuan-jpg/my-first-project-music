## 1. 项目概述

### 1.1 项目目标

开发一款 Android 原生 App，以"竖屏跑酷游戏"的形式训练用户的歌唱音准。用户对着手机麦克风演唱，App 实时检测人声音高频率，将音高映射为游戏角色的垂直位置，角色需在滚动的"台阶"上准确落脚——每个台阶对应乐谱中的一个音符。唱准则通过，唱偏则坠落或miss。App 导入用户提供的 MusicXML 乐谱，自动解析并生成游戏地图，以"小节"为最小进度单位，每完成一小节自动存档。

### 1.2 目标用户

- 歌唱初学者、合唱团成员、乐器学习者需要视唱练耳的用户
- 希望以游戏化方式练习音准的业余爱好者
- 区分男声 / 女声自然音域，提供八度适配

### 1.3 核心玩法一句话

**唱什么音，角色就到什么高度；音符台阶从屏幕上方（高频）向下方（低频）排列，唱准当前小节所有音符即过关并自动存档。**

### 1.4 v1 推荐技术栈（可替换，需满足 KPI）

> 以下为 v1 推荐技术栈，不是硬约束。可在满足第 5.1 节硬性规则和第 7 章验收项的前提下替换为更优方案，详见第 4 章 ADR 替换规则。

| 层级 | 技术 | 说明 |

### 1.5 范围边界

**In Scope（v1）**
- MusicXML 导入与解析（单声部旋律为主）
- 麦克风实时音高采集与 YIN 检测

- 歌词同步显示

- 曲库搜索 / 筛选 / 自定义排序（v1 仅按最近游玩时间排序）
- 伴奏音乐 / 人声分离（v1 仅节拍器引导，无伴奏）
- 多用户档案 / 家庭成员切换

## 2. Glossary 术语表

> 术语分为两类：**通用术语**（产品概念，任何技术实现都适用）和 **v1 推荐实现术语**（绑定具体技术方案，替换技术后可能不再适用，标注 〔v1〕）。

| 术语 | 英文/缩写 | 定义 |
|---|---|---|
| 台阶 | Step / Platform | 游戏中水平放置的落脚平台，每个台阶对应一个半音（1 个 MIDI 编号）的音高位置。台阶在屏幕上从上到下排列，越靠下频率越低 |
| 小节 | Measure / Bar | 乐谱的基本节奏单位，以拍号分隔。本 App 以小节为最小进度与存档单位 |
| 音符 | Note | 乐谱中的单个音，包含音高（音名+八度）、时值、起止时间 |
| 音高 | Pitch | 声音的基频，单位 Hz；本 App 内部统一用**浮点 MIDI 编号**表示 |
| 浮点 MIDI | Float MIDI | MIDI 编号的浮点扩展，公式 `midi = 69 + 12 × log2(f/440)`。保留小数以反映音分偏差，**不四舍五入为整数** |
| 音分 | Cent | 音高偏差单位，1 半音 = 100 音分。用于判定唱准的容差 |
| 目标音高 | Target Pitch | 当前音符要求演唱的音高（经八度偏移后） |
| 当前音高 | Current Pitch | 麦克风实时检测到的用户音高（浮点 MIDI） |
| 游戏地图 | Game Map | 由 MusicXML 解析生成的关卡数据，包含所有音符台阶的位置、时值、小节划分 |
| 存档点 | Checkpoint | 小节边界处的自动存档位置，记录已完成小节数与准确率 |
| 节奏窗口 | Rhythm Window | 每个音符允许的起始时间偏差范围（ms），在此窗口内开始演唱且音高达标方判定为命中 |
| 音高容差 | Pitch Tolerance | 判定"唱准"允许的最大音分偏差，默认 ±50 音分，练习模式 ±75 音分 |
| 练习模式 | Practice Mode | 默认开启的游戏模式：不强制失败、可暂停、显示引导线、容差较宽松，用于学习 |
| 挑战模式 | Challenge Mode | 练习模式关闭后的严格模式：固定速度、严格容差、miss 累计达阈值则本小节失败需重唱 |
| 命中 | Hit | 音符在节奏窗口内开始演唱，且持续期间音高在容差范围内的比例达标 |
| Miss | 未命中 | 音符未在节奏窗口内演唱，或音高偏差超出容差 |
| YIN 算法 〔v1〕 | YIN | aubio 实现的基频检测算法，基于自相关函数差分，适合单声部人声。替换检测算法后此术语可能不再适用 |
| 浊音/清音判定 | Voiced/Unvoiced | 判断当前帧是否为有声音高（说话/歌唱）而非噪音、呼吸或静音 |
| 八度偏移 | Octave Shift | 针对男声自然比女声低约八度的特性，对目标音高施加的 ±12 半音整数偏移。例如谱子记谱 C4 时，女声唱 C4（偏移 0），男声唱 C3（偏移 -12） |
| 后处理流水线 〔v1〕 | Post-processing Pipeline | 对音高检测原始输出依次进行：浊音判定 → 八度纠错 → 中值滤波 → 平滑 → 浮点 MIDI 转换的处理链 |
| MusicXML | MusicXML | 一种基于 XML 的乐谱交换格式，支持 .xml（未压缩）和 .mxl（zip 压缩） |
| 角色/物品 | Avatar | 玩家控制的游戏对象，可为小人、水果或其他抽象物品，仅视觉差异，不影响判定 |
| 全局进度 | Overall Progress | 已完成小节数 / 总小节数的百分比 |
| 小节内进度 | Measure Progress | 当前小节内已命中音符数 / 本小节音符数 |
| 节拍器 | Metronome | 游戏中提供节奏引导的滴答声，练习模式默认开启，与滚动速度严格同步 |
| 可视时间窗口 | Visible Time Window | 屏幕内能显示的未来乐谱时长，v1 要求 ≥4 秒（约 2 小节） |
| 游戏评级 | Grade | 全曲完成后的综合评价，S/A/B/C/D 五档，基于准确率和平均偏差 |
| 新手教程 | Onboarding Tutorial | 首次启动时的交互式引导，含玩法说明、坐标解释和实操练习 |
| 位置存档 | Position Save | 每次小节边界保存的当前进度索引，用于异常退出后恢复到该小节（无论是否通过） |
| 完成存档 | Completion Save | 仅小节通过时保存的学习记录，用于进度统计和曲库展示 |
| 前端处理链 〔v1〕 | Front-end Processing Chain | 音频采集后、音高检测前的信号处理链，含高通滤波、噪音抑制(NS)、自动增益控制(AGC)、削波检测 |
| 双算法融合 〔v1〕 | Dual-algorithm Fusion | 同时运行 YIN 和 fcomb 两个检测器，按置信度加权融合，降低八度错误率 |
| 浊音判定 | Voiced/Unvoiced Detection | 判断当前帧是否为有调人声，基于置信度+能量门限+削波检测三重判定 |
| 颤音检测 | Vibrato Detection | 检测周期性 ±20–40 音分、5–8Hz 的音高波动，识别后降低平滑系数保留自然颤音 |
| 削波 | Clipping | 输入音量过大导致信号顶部/底部被削平，标记为不可靠帧 |
| 音域校准 | Range Calibration | 用户唱高低音各 3 秒，确定个人音域 [f_min, f_max]，用于八度纠错和频率约束 |
| 环境噪音基线 | Noise Floor | 游戏开始前 2 秒静默采样得到的环境噪音水平，用于自适应浊音判定阈值 |
| 小节练习模式 | Measure Loop Mode | 用户选择单个或连续小节范围，循环重复练习的模式，不影响全曲进度存档 |
| 最弱小节推荐 | Weakest Measure Recommendation | 系统自动列出用户历史准确率最低的 3 个小节，引导用户针对性练习 |
| 检测质量 | Detection Quality | 实时评估当前音高检测结果的可靠程度，基于置信度、稳定性、削波率、浊音率综合计算，分为高/中/低/不可用四级 |
| 质量加权判定 | Quality-weighted Judgment | 判定命中时按每帧检测质量加权计算平均音高，低质量帧降低权重，不可用帧跳过判定，避免检测不稳定导致误判 |
| 显示用音高 | Display Pitch | 用于屏幕显示的原始浮点 MIDI 值，保留用户真实演唱的波动和偏差 |
| 判定用音高 | Judgment Pitch | 用于命中判定的质量加权后音高值，经过平滑和容错处理，保证判定公平性 |
| 领域层 | Domain Layer | 业务逻辑层，包含实体、用例、仓储接口和 UI 接口，与 UI 框架解耦，可独立单元测试 |
| 表示层 | Presentation Layer | UI 层，负责 Widget 渲染和用户交互，实现 Domain 层定义的接口 |
| 数据层 | Data Layer | 负责 MusicXML 解析、SQLite/SP 读写，实现 Domain 层的仓储接口 |
| UI 接口 | UI Interface | Domain 层定义的抽象类（GameRenderer/AudioFeedback/GameStateCallback/AppNavigation），由 Presentation 层实现，业务逻辑通过接口调用 UI |

## 3. Spec 功能规格

> 每条规格统一包含：**用户操作 → 系统行为 → 成功 → 失败 → 异常表现**

### 3.1 乐谱导入与解析

**用户操作**
1. 在首页点击"导入乐谱"按钮
2. 通过系统文件选择器选择 `.xml` 或 `.mxl` 文件
3. （多声部时）选择要演奏的声部
4. 确认导入

**系统行为**
1. 校验文件扩展名与文件头（.mxl 需解压）
2. 解析 MusicXML：识别 `score-partwise` 结构，提取声部、小节、音符、拍号、调号、速度标记
3. 将每个音符转换为内部模型：`{ midi_float, start_time_ms, duration_ms, measure_index, is_rest, is_chord }`
4. 按小节分组，计算每小节的起始时间与结束时间
5. 若乐谱含和弦，默认取最高音为旋律音（可在导入时切换为最低音）
6. **持久化保存**：
   - 将原始乐谱文件复制到 App 私有目录 `files/scores/` 下（以文件哈希命名，避免重复存储）
   - 保存解析后的游戏地图到 SQLite，记录文件哈希、原始文件名、文件路径以防重复导入
7. 返回首页曲库列表，显示新导入曲目
8. 曲库数据持久化存储，下次启动 App 时自动加载所有已导入乐谱，用户可直接点击打开，无需重新导入文件

**成功**
- 曲库中出现该乐谱，可点击进入游戏
- 解析日志无 fatal error
- 总小节数、总音符数正确显示

**失败**
- 文件格式不支持 → Toast 提示"仅支持 MusicXML (.xml/.mxl) 格式"
- 文件损坏 / XML 解析异常 → 提示"乐谱文件解析失败，请检查文件完整性"
- 文件为空 / 无音符 → 提示"未在乐谱中检测到音符"
- 重复导入 → 提示"该乐谱已导入"，并跳转到已有条目

**异常表现**
- .mxl 解压失败 → 按文件损坏处理
- 含不支持的 MusicXML 元素（如 `<forward>`、复杂连音）→ 跳过该元素并记录 warning，不阻断导入；在曲目详情页显示"解析警告 N 条"
- 拍号/调号在中途变化 → 以变化点为界分段处理，速度取最近的 `<sound tempo>` 标记，无标记时默认 120 BPM

### 3.2 游戏地图生成

**用户操作**
- 在曲库中点击某乐谱 → 进入游戏准备页 → 点击"开始"

**系统行为**
1. 从 SQLite 读取该乐谱的游戏地图数据
2. 应用用户当前设置：八度偏移、音高容差、节奏窗口、滚动速度倍率
3. **竖屏可视区域计算**：
   - 屏幕宽度（dp）决定水平可视时间窗口：`可视秒数 = 屏幕宽度dp / 像素每毫秒`
   - 必须保证可视区域 ≥ 未来 4 秒乐谱（约 2 小节，4/4 拍 60BPM），用户有足够准备时间
   - 若屏幕宽度不足（如小屏手机 <360dp），自动降低每毫秒像素密度以保证 4 秒窗口，台阶最小宽度不低于 12dp
4. 将每个音符映射为屏幕坐标：
   - **X 坐标** = 音符起始时间 × 水平像素/毫秒（由 BPM 与速度倍率决定）
   - **水平像素/毫秒** = `(屏幕宽度dp × 0.7) / (4秒 × 1000)`，即角色位于屏幕左侧 30% 处，右侧 70% 显示未来音符
   - **Y 坐标** = (最高显示MIDI - 目标浮点MIDI) × 每半音像素高度 + 顶部偏移（屏幕顶部 = 高频，底部 = 低频）
5. 台阶宽度 = 音符时值 × 水平像素/毫秒（最小宽度 12dp）
6. 小节分隔线绘制在每小节起始 X 位置
7. **节拍引导**：
   - 游戏开始前 3 秒倒计时，同时播放节拍器"滴答"声（练习模式默认开启，挑战模式默认关闭）
   - 每小节第一拍有视觉重音提示（小节线闪烁 + 低音"咚"）
   - 第一个音符前 1 秒显示"准备"提示，音符到达角色位置时显示"唱"提示
8. 生成游戏循环（Ticker），角色从左向右自动推进，角色固定在屏幕左侧 30% 位置，地图向左滚动

**成功**
- 台阶位置与乐谱音符一一对应
- 小节线清晰可见
- 角色初始位置位于屏幕左侧 30%，第一音符在角色右侧 4 秒处
- 可视区域至少显示未来 4 秒乐谱
- 倒计时结束后节拍器与角色滚动同步启动

**失败**
- 地图数据缺失 → 提示"地图数据损坏，请重新导入乐谱"
- 音符超出屏幕音高范围（默认 C1–C8，MIDI 12–108）→ 自动扩展可视音域或提示"乐谱音域超出显示范围"
- 屏幕宽度过小无法保证 4 秒窗口且台阶宽度 <12dp → 提示"屏幕过小，建议使用更大屏幕设备"

**异常表现**
- 休止符 → 不生成台阶，保留空白间隔，节拍器继续
- 连音/附点 → 按时值精确计算台阶宽度
- 速度变化 → 滚动速度在对应时间点平滑过渡（不跳变），节拍器 BPM 同步变化
- 弱起小节 → 第一个音符前的空白按实际时值保留，倒计时在弱起拍前结束

### 3.3 麦克风音高采集与检测

**用户操作**
- 首次进入游戏时授权麦克风权限
- 对着麦克风演唱

**系统行为**

> 以下技术实现（Oboe、aubio YIN+fcomb、前端处理链、后处理流水线）及具体参数为 **v1 推荐方案**。开发 AI 可在满足 HR-02（延迟）、HR-10/HR-11（准确性）等硬性规则的前提下，替换为更优算法或调优参数，并记录为新 ADR。

### 3.3.1 音频采集与前端处理链

1. 通过 Oboe 以低延迟模式打开麦克风输入流
   - 采样率：优先 48000 Hz，回退 44100 Hz
   - 声道：单声道
   - 帧大小：Oboe 自动选择最低可用 burst size
   - 输入源：`VOICE_RECOGNITION`（Android 音频源，针对人声优化，自带基础 AEC/NS）
2. **麦克风选型策略**：
   - 优先使用手机底部内置麦克风（延迟最低、人声采集最优）
   - 有线耳机带麦时：自动切换耳机麦克风（更接近嘴部，噪音更少）
   - 蓝牙麦克风：默认不使用（延迟高、压缩算法影响音高），用户可在设置中手动开启
   - USB 麦克风：优先使用（专业级音质），可在设置中切换
3. **前端处理链（按顺序，均在 C++ 层完成，避免 JVM 延迟）**：
   - **高通滤波**：截止频率 70Hz，滤除低频环境噪音（空调、风声、手持摩擦），不影响人声基频（男声最低 ~85Hz）
   - **噪音抑制（NS）**：基于谱减法，抑制稳态环境噪音，处理强度自适应（安静环境弱、嘈杂环境强）
   - **自动增益控制（AGC）**：将输入音量归一化到 -16dBFS，避免用户音量过小导致检测失败，或过大导致削波
   - **削波检测**：检测到信号削波（clipping）时标记该帧不可靠，降低置信度
4. 处理后的音频帧通过 FFI 传入音高检测层

### 3.3.2 多算法融合音高检测

5. **双算法并行检测**（同一音频帧同时跑两个算法，取置信度高者）：
   - **主检测器：YIN**
     - buffer size：2048 samples（48kHz 下约 42.7ms，保证低频检测精度）
     - hop size：512 samples（约 10.7ms，~93Hz 检测率）
     - 置信度阈值：0.7
   - **校验检测器：fcomb**（aubio 内置，基于谐波组合，对高频更敏感）
     - 相同 buffer/hop 参数
     - 用于校验 YIN 结果，特别是八度错误
6. **算法融合策略**：
   - YIN 置信度 ≥0.7 且 fcomb 结果与 YIN 偏差 <50 音分 → 采用 YIN 结果，置信度加权 = YIN_conf × 0.7 + fcomb_conf × 0.3
   - YIN 置信度 ≥0.7 但 fcomb 偏差 ≥50 音分 → 标记为"不确定"，采用 YIN 结果但置信度降为 0.5
   - YIN 置信度 <0.7 但 fcomb 置信度 ≥0.7 → 采用 fcomb 结果
   - 两者置信度均 <0.7 → 判定为 unvoiced（静音/噪音）
7. **频率范围约束**：
   - 检测结果限制在 70Hz–1200Hz（覆盖人声 C2–C6，MIDI 36–96）
   - 超出范围直接丢弃，避免高频泛音误判

### 3.3.3 后处理流水线

8. 后处理流水线依次执行：
   - **浊音判定**：融合后置信度 <0.5 或能量过低（RMS<0.005）或削波 → 当前帧标记为 unvoiced，不更新音高
   - **八度纠错**：
     - 若检测频率与上一帧差异超过 1.9 倍且新频率在上一帧的 2 倍/半倍附近 → 触发纠错
     - 结合用户音域先验（男声基频 <250Hz 合理，女声 <500Hz 合理）
     - 结合 fcomb 校验结果：若 fcomb 支持低八度则修正为低八度，支持高八度则保持
     - 纠错后置信度降为 0.6
   - **连续性约束**：连续 3 帧以上同一方向的八度跳变才接受，单帧跳变视为尖峰丢弃
   - **中值滤波**：取最近 3 帧浮点 MIDI 的中值，消除瞬时尖峰
   - **颤音检测与保护**：
     - 检测到周期性 ±20–40 音分波动且频率 5–8Hz → 判定为颤音（vibrato）
     - 颤音期间降低平滑系数至 α=0.1，保留自然波动
     - 非颤音期间使用 α=0.3 正常平滑
   - **平滑**：指数移动平均，颤音期 α=0.1，正常期 α=0.3，引入延迟 <15ms
   - **起音保护**：音符起始后前 2 帧（~21ms）不参与判定，允许起音不稳定
   - **浮点 MIDI 转换**：`midi = 69 + 12 × log2(f/440)`，保留全部小数位
9. 将浮点 MIDI 通过 Stream 传递给游戏渲染层与判定层
10. **禁止**将浮点 MIDI 四舍五入为整数（不自动纠错）

### 3.3.4 环境自适应与校准

11. **环境噪音自适应**：
    - 游戏开始前 2 秒静默采样，计算环境噪音基线（RMS 和频谱）
    - 根据噪音水平动态调整浊音判定能量阈值：安静环境 0.005，嘈杂环境最高 0.02
    - 噪音持续 >60dB 时提示"环境噪音较大，建议佩戴耳机或到安静处练习"
12. **用户音域校准**（首次启动或设置中手动触发）：
    - 引导用户唱舒适的低音 3 秒 + 高音 3 秒
    - 取稳定段中位频率，确定用户音域范围 [f_min, f_max]
    - 音域先验用于八度纠错和频率范围约束
    - 校准结果保存到 SharedPreferences，可随时重新校准
13. **设备麦克风校准**：
    - 首次使用时检测麦克风频率响应（播放/不需要，仅检测输入灵敏度）
    - 记录设备型号对应的 AGC 参数，避免不同设备音量差异过大

**成功**
- 演唱稳定音时，当前音高指示线稳定在目标音高附近，偏差 <10 音分
- 标准音 440Hz 检测值在 438–442Hz 范围内
- 人声连续演唱时八度错误率 <2%
- 静音时不产生虚假音高
- 端到端延迟 <100ms（P50）

**失败**
- 麦克风权限被拒 → 显示权限引导页，无法开始游戏
- 麦克风被其他应用占用 → Oboe 打开失败，提示"麦克风被占用，请关闭其他录音应用后重试"
- 检测持续失败（>10 秒无有效音高）→ 提示"未检测到声音，请检查麦克风或增大音量"

**异常表现**
- 检测到八度跳变（常见于男声低音区，YIN 误判为二次谐波）→ 八度纠错模块结合 fcomb 校验和音域先验修正；若纠错后仍不稳定，在音高线上以虚线/灰色显示"检测不稳定"
- 环境噪音大 → 自适应阈值过滤无调噪音，音高线在静音段保持最后有效值或淡出；噪音 >60dB 时提示
- 颤音（vibrato）→ 检测到颤音后降低平滑系数，保留 ±20–40 音分自然波动，不被过度抹平
- 起音瞬间（辅音 b/p/d/t）→ 前 2 帧不参与判定，允许不稳定
- 信号削波（音量过大）→ 标记不可靠帧，降低置信度，提示"音量过大，请适当远离麦克风"
- 假声/哨音（高频 >800Hz）→ fcomb 辅助检测，YIN 可能不稳定时切换到 fcomb 结果

### 3.3.5 运行时质量监控与判定层容错

> **核心原则**：检测层输出原始浮点 MIDI（保证真实性，HR-01），判定层使用质量加权后的音高（保证公平性）。低质量帧不得直接导致 miss。

1. **实时质量指标计算**（每帧更新，滑动窗口 30 帧 ≈320ms）：
   - 平均置信度：最近 30 帧融合后置信度的均值
   - 稳定性：最近 30 帧浮点 MIDI 的标准差，<15 音分为稳定，15–40 为一般，>40 为不稳定
   - 削波率：最近 30 帧中削波帧占比
   - 浊音率：最近 30 帧中 voiced 帧占比

2. **质量分级**：
   - 高质量（Q=1.0）：平均置信度 >0.7，稳定性 <15 音分，削波率 <5%
   - 中质量（Q=0.7）：平均置信度 0.5–0.7，或稳定性 15–40 音分
   - 低质量（Q=0.3）：平均置信度 <0.5，或稳定性 >40 音分，或削波率 >20%
   - 不可用（Q=0）：连续 10 帧 unvoiced，或削波率 >50%

3. **判定层容错机制**：
   - 音符持续期间，使用质量加权平均音高：`weighted_pitch = Σ(pitch_i × Q_i) / ΣQ_i`
   - 低质量帧（Q<0.5）不直接判 miss，而是降低权重
   - 不可用帧（Q=0）不参与判定，音符判定窗口自动延长对应时长
   - 当整体质量 <0.5 持续 >2 秒时，暂停判定并提示"当前检测质量较差，建议调整位置或音量"

4. **显示与判定分离**：
   - 显示用音高线：原始浮点 MIDI（含波动和偏差），让用户看到真实演唱
   - 判定用音高：质量加权后的平滑值，保证判定公平
   - 两者在 UI 上可区分：显示线为实线，判定参考线为虚线或半透明

5. **质量反馈 UI**：
   - 屏幕角落显示实时质量指示器（绿/黄/红三色圆点）
   - 低质量时显示提示文字："检测不稳定，请靠近麦克风或减小环境噪音"
   - 削波时提示"音量过大，请适当远离麦克风"

### 3.4 角色控制与台阶移动

**用户操作**
- 通过演唱不同音高控制角色垂直位置
- 角色水平方向自动向前滚动（不可手动控制）

**系统行为**
1. 角色垂直位置 = 当前音高（浮点 MIDI）映射到屏幕 Y 坐标
   - 映射公式：`y = (最高显示MIDI - currentMidi) × 每半音像素 + 顶部偏移`
   - 即：音高越高 → y 越小 → 越靠近屏幕顶部（符合"台阶从上到下频率依次减小"）
2. 角色水平位置随游戏时间匀速推进（速度由 BPM 决定）
3. 当角色 X 坐标进入某个台阶的 X 范围时，进行命中判定：
   - 若角色 Y 在台阶 Y ± 容差范围内 → 命中，角色落在台阶上，播放踩踏反馈
   - 若角色 Y 高于台阶（唱太高，位置偏上）→ 角色从台阶**上方越过**，踩空，台阶显示"偏高"
   - 若角色 Y 低于台阶（唱太低，位置偏下）→ 角色从台阶**下方穿过**，坠落，台阶显示"偏低"
4. 命中时播放视觉反馈（台阶高亮、粒子效果）；miss 时角色闪烁/变暗
5. 角色皮肤可在设置中切换（小人 / 苹果 / 西瓜等），仅视觉不同

**成功**
- 唱准目标音时，角色准确落在对应台阶上
- 音高变化时角色垂直移动平滑、跟手
- 水平滚动速度与乐谱节拍一致

**失败**
- 连续 miss 超过阈值（挑战模式：本小节 miss ≥ 3 或命中率 < 60%）→ 本小节判定失败，自动回退到小节开头重唱
- 练习模式下不触发失败回退，仅记录 miss

**异常表现**
- 音高超出显示范围 → 角色到达屏幕边缘后停止移动，边缘显示箭头提示"音偏高/低"
- 快速滑音（glissando）→ 角色应连续移动，不应台阶式跳变
- 静音/呼吸 → 角色保持最后位置并逐渐变暗，恢复演唱后恢复

### 3.5 小节判定与自动存档

**用户操作**
- 演唱当前小节的所有音符
- 小节结束后系统自动处理，无需用户操作

**系统行为**
1. 以小节为单位收集命中结果
2. 当角色 X 越过小节分隔线（即当前小节所有音符时间窗均已过）时触发小节结算：
   - 统计本小节：总音符数、命中数、miss 数、平均音分偏差、平均延迟
   - **判定通过条件**：命中率 ≥ 60%（练习模式）或 ≥ 80%（挑战模式），且无连续 miss ≥ 3
3. **自动存档逻辑（双层，职责分离）**：
   - **位置存档（每次小节边界必存，无论是否通过）**：
     - 保存字段：`current_measure_index`（当前小节索引）、`settings_snapshot`（当前设置快照）、`saved_at`（时间戳）
     - 作用：记录用户"玩到了第几小节"，用于异常退出后恢复到该小节，而非从头开始
     - 写入时机：小节结算完成后立即同步写入（await）
   - **完成存档（仅小节通过时存）**：
     - 保存字段：`measure_index`、`passed=true`、`hit_count`、`avg_cents`、`completed_at`
     - 作用：记录学习成果，驱动全局进度条和曲库统计
   - **恢复逻辑（启动时）**：
     - 读取位置存档的 `current_measure_index`
     - 查完成存档：若该小节已通过 → 从下一小节开始；若未通过 → 从该小节开头重唱
     - 若位置存档损坏或缺失 → 从第 1 小节开始
4. 存档写入 SQLite，事务保证原子性，写入后立即 fsync
5. 小节通过时显示"小节完成！准确率 XX%"动画 1.5 秒，然后自动进入下一小节
6. 小节未通过（挑战模式）→ 显示"再试一次"，回退到本小节开头，不标记完成，位置存档仍更新为当前小节索引

**成功**
- 唱准一小节后，全局进度 +1 小节，存档自动完成
- 杀进程后重新进入，可从最近通过的小节继续
- 存档数据在曲库详情页可见（已通过 X/Y 小节，平均准确率）

**失败**
- 存档写入失败（磁盘满 / SQLite 错误）→ Toast 提示"存档失败，请检查存储空间"，当前进度保留在内存中，下次小节边界重试
- 数据损坏 → 检测到存档校验和不匹配时，回退到上一个有效存档点，并提示"存档已恢复到较早位置"

**异常表现**
- 小节内只有休止符 → 自动通过，不要求演唱
- 小节内含和弦 → 仅判定选定的旋律音（默认最高音）
- 用户在小节中途暂停 → 不触发结算，恢复后从暂停时间点继续
- 最后一小节结束 → 触发全曲完成结算，显示总准确率与评级，存档标记全曲完成

### 3.6 音高可视化（当前 vs 目标）

**用户操作**
- 游戏过程中自然观察屏幕

**系统行为**
1. **目标音高显示**：
   - 每个台阶左侧/上方标注音名（如 C4、F#4）
   - 当前即将到达的台阶高亮显示
   - 台阶颜色按音高分组（一个八度内循环配色）
2. **当前音高显示**：
   - 角色本身即当前音高的垂直位置指示
   - 角色旁绘制一条水平音高指示线，延伸至屏幕左边缘的音高标尺
   - 音高标尺显示 MIDI 编号 / 音名 / 频率 Hz
   - 最近 2 秒的音高轨迹以半透明曲线绘制在角色后方（类似 Singscope 的滚动音高曲线）
3. **偏差反馈**：
   - 当角色接近目标台阶时，台阶边缘显示偏差方向：偏高（↓箭头，红色）/ 偏低（↑箭头，蓝色）/ 准（绿色对勾）
   - 偏差数值以音分显示（如 +23 cents）
4. 练习模式下额外显示：目标音高的水平引导虚线（贯穿屏幕），帮助用户找到位置

**成功**
- 用户能直观看到自己唱的音高与目标音高的相对位置和偏差
- 音高轨迹曲线平滑，反映真实演唱波动
- 标尺读数与实际音高一致

**失败**
- 渲染掉帧 → 音高线卡顿；需保证 60fps 渲染，音高数据更新与渲染解耦（数据 93Hz，渲染 60Hz 插值）

**异常表现**
- 当前音高为静音（unvoiced）→ 音高线淡出，轨迹断开，不显示偏差
- 八度偏移生效时 → 标尺同时显示原始乐谱音高与实际演唱音高（括号标注），避免用户困惑

### 3.8 男声 / 女声八度适配

**用户操作**
- 首次启动时选择"男声"或"女声"
- 可在设置中随时切换
- 可手动微调八度偏移（-24 / -12 / 0 / +12 / +24 半音）
- 可选执行"音域校准"：唱几个舒适的音，App 自动计算最佳偏移

**系统行为**
1. 预设偏移：
   - 女声 → 默认偏移 0（乐谱通常按女声/高音谱号记谱）
   - 男声 → 默认偏移 -12（低八度演唱）
2. **男女音高对应关系（核心规则）**：以乐谱记谱音高为基准，男声实际演唱音高比女声低一个八度。例如谱子记谱为 **C4** 时：
   - 女声用户演唱 **C4**（octave_shift = 0，effective_target = C4）
   - 男声用户演唱 **C3**（octave_shift = -12，effective_target = C3）
   - 两者在游戏中落在同一个视觉台阶位置，判定均为"唱准"
3. 偏移应用于**目标音高**：`effective_target = sheet_midi + octave_shift`
4. 判定时使用 effective_target 与用户当前音高比较
5. 可视化时：台阶位置按 effective_target 绘制，同时在标尺上标注原始乐谱音名（如"C4（乐谱记谱）→ C3（男声实际演唱）"）
6. **音域校准流程**：
   - 提示用户用舒适音量唱"啊——"保持 3 秒
   - 取稳定段的中位频率作为用户基准音高
   - 与乐谱的主音/中央 C 比较，计算最接近的整数八度偏移
   - 预览偏移效果，用户确认后保存

**成功**
- 男声用户演唱时，角色能落在与女声用户相同的视觉台阶位置（实际频率低八度）
- 切换声线后立即生效，无需重启

**失败**
- 校准时检测不到稳定音高 → 提示"未检测到清晰音高，请在安静环境重试"，保留当前偏移设置

**异常表现**
- 用户音域跨八度（假声）→ 八度纠错模块应允许合理范围内的八度跳变，不强制拉回
- 乐谱本身已为男声移调（如低音谱号）→ 用户可手动将偏移设为 0

### 3.9 练习模式（默认开启）

**用户操作**
- 设置中切换"练习模式"开关（默认 ON）

**系统行为**

| 维度 | 练习模式（ON） | 挑战模式（OFF） |
|---|---|---|
| 音高容差 | ±75 音分 | ±50 音分 |
| 节奏窗口 | ±300ms | ±200ms |
| 失败回退 | 不回退，miss 仅记录 | 命中率 <80% 回退重唱 |
| 引导线 | 显示目标音高水平虚线 | 不显示 |
| 滚动速度 | 可 0.5x–1.0x 调节 | 固定 1.0x |
| 节拍器声音 | 开启（可选关闭） | 关闭 |
| 暂停 | 可随时暂停 | 可暂停但暂停次数记录 |

**成功**
- 新用户默认进入练习模式，体验友好
- 切换后下一小节生效（当前小节结算后应用）

### 3.10 角色/物品皮肤与设置

**用户操作**
- 设置页选择角色皮肤（小人 / 苹果 / 西瓜 / 篮球等，至少 3 种）
- 调节音量（伴奏/提示音，v1 无伴奏，仅判定反馈音）
- 切换练习模式
- 切换声线 / 八度偏移
- 调节容差难度（简单/普通/困难，对应 ±75/±50/±25 音分）

**系统行为**
- 设置保存到 SharedPreferences
- 皮肤切换立即在游戏预览中生效
- 难度调节覆盖练习/挑战模式的默认容差

### 3.11 曲库管理（重命名 / 删除）

**用户操作**
1. 在首页曲库列表中，长按某曲目卡片，或点击曲目卡片右侧的"更多"（⋮）按钮
2. 弹出操作菜单："重命名" / "删除" / "查看详情"
3. 选择"重命名" → 弹出输入框，输入新名称 → 确认
4. 选择"删除" → 弹出确认对话框 → 确认删除

**系统行为**
1. 曲库列表从 SQLite 读取所有已导入乐谱，按最近游玩时间排序
2. **重命名**：更新 SQLite 中该曲目的 `display_name` 字段，原始文件名与文件哈希保持不变；重命名即时生效
3. **删除**：
   - 若该曲目存在练习进度，弹出二次确认："删除后该乐谱的练习进度将一并清除，确定删除吗？"
   - 确认后：删除 SQLite 中该曲目记录、关联的小节进度记录，以及私有目录 `files/scores/` 下的原始乐谱文件
   - 曲库列表即时刷新
4. **查看详情**：跳转曲目详情页，显示总小节数、已通过小节数、平均准确率、最近游玩时间、解析警告

**成功**
- 重命名后曲库列表中显示新名称，进入游戏后标题栏同步更新
- 删除后曲库列表中该曲目消失，存储空间释放
- 重复导入同一文件时，若原文件已被删除则允许重新导入

**失败**
- 重命名名称为空 → 提示"名称不能为空"
- 重命名名称超过 50 字符 → 提示"名称不能超过 50 个字符"
- 删除时文件已不存在（外部清理）→ 仅删除 SQLite 记录，提示"乐谱文件已不存在，已移除记录"

**异常表现**
- 重命名为与已有曲目相同名称 → 允许（以 ID 区分，不强制唯一），但建议在名称后自动追加序号
- 删除过程中 App 崩溃 → 下次启动时检测到孤儿记录（SQLite 有记录但文件不存在）或孤儿文件（文件存在但 SQLite 无记录），自动清理

### 3.12 游戏结算与反馈

**用户操作**
- 唱完最后一小节后自动进入结算页，无需用户操作
- 在结算页可选择"再唱一次"、"返回曲库"、"查看详情"

**系统行为**
1. 最后一小节结算完成后，停止滚动与音频采集，进入结算页
2. **结算统计**：
   - 总准确率 = 总命中音符数 / 总音符数 × 100%
   - 总音分偏差 = 所有命中音符的偏差绝对值的平均值
   - 各小节通过状态列表（通过/未通过/未唱）
   - 最佳小节（准确率最高）与最弱小节（准确率最低）
   - 练习时长
3. **评级标准**：
   - S：准确率 ≥ 95% 且平均偏差 < 15 音分
   - A：准确率 ≥ 85%
   - B：准确率 ≥ 70%
   - C：准确率 ≥ 50%
   - D：准确率 < 50%
4. **可视化反馈**：
   - 全曲音高轨迹缩略图（用户演唱音高 vs 目标音高的偏差热力图）
   - 偏差分布饼图（偏低/准/偏高占比）
   - 各小节准确率柱状图
5. 保存本次游戏记录到 SQLite（GameRecord 表），用于历史统计
6. 结算页操作：
   - [再唱一次] → 从第 1 小节重新开始（不清除已通过记录，本次为新的一次练习）
   - [返回曲库] → 回到首页曲库列表
   - [查看详情] → 展开各小节详细数据，点击某小节直接进入该小节的重复练习（跳转到 3.13 小节选择界面并预选中该小节）

**成功**
- 结算页显示完整统计与评级
- 游戏记录已保存，可在曲库详情页查看历史
- 再唱一次后游戏正常从头开始

**失败**
- 统计计算异常（除零等）→ 显示"统计生成失败"，仍可返回曲库，游戏记录不保存
- 保存记录失败 → 提示"记录保存失败"，不影响结算页显示

**异常表现**
- 用户在最后一小节前退出 → 不触发全曲结算，仅保存位置存档
- 全曲无命中音符（全 miss）→ 评级 D，偏差统计显示"无有效数据"
- 乐谱只有 1 个小节 → 结算页仍正常显示，柱状图仅 1 根

### 3.13 小节选择与重复练习

**用户操作**
- 在游戏准备页点击「选择小节练习」
- 在小节选择界面单选或框选连续小节范围
- 练习中可暂停、退出、调整循环次数
- 单次循环结束后选择「再来一次」或「退出」

**系统行为**

### 3.13.1 小节选择界面

1. 游戏准备页增加按钮「选择小节练习」（位于「开始」按钮下方）
2. 点击后进入小节选择界面：
   - 顶部显示曲目名 + "选择要练习的小节"
   - 中部为小节缩略图列表（横向滚动），每个缩略图显示：
     - 小节序号
     - 音符概览（简化的台阶预览）
     - 历史准确率（若有），颜色编码：绿≥85%、黄 50–85%、红<50%、灰=未练习
     - 通过状态标记（✓ 已通过）
   - 底部：已选范围显示（如"第 3–5 小节"）、「全选」「清除」按钮、「开始练习」按钮
3. **选择方式**：
   - 单击单个小节 → 选中该小节
   - 长按第一个小节后拖动 → 框选连续范围
   - 已选小节高亮显示，再次点击取消
   - 支持不连续选择吗？**v1 仅支持单个小节或连续范围**，不支持不连续多选
4. 选择完成后点击「开始练习」→ 进入小节练习模式

### 3.13.2 小节练习模式

5. 进入游戏，地图仅包含选中的小节，其他小节不生成
6. **循环设置**（练习前可在准备页设置，练习中暂停菜单可改）：
   - 循环次数：无限循环 / 固定 3 次 / 固定 5 次 / 自定义 1–10 次
   - 默认：无限循环（用户手动退出）
   - 循环间隔：每次循环结束后显示 2 秒结算，然后自动开始下一次
7. **单次循环流程**：
   - 3 秒倒计时 → 节拍器预响 → 开始
   - 选中的小节依次滚动
   - 最后一个小节结束 → 停止滚动 → 显示本次循环结算浮层 2 秒：
     - 本次准确率
     - 与上一次对比（↑提升 / ↓下降 / —持平）
     - 命中/ miss 音符数
   - 自动开始下一次循环（若未达设定次数）
8. **练习中暂停菜单**（比普通模式增加选项）：
   - 继续
   - 重新开始本次循环
   - 调整循环次数
   - 更换选中小节（返回小节选择界面）
   - 退出到曲库

### 3.13.3 存档与统计

9. **存档规则**：
   - 小节练习模式**不更新全曲位置存档**（PositionSave 不变）
   - 小节练习模式**不更新全曲完成存档**（MeasureProgress.passed 不变）
   - 每次循环结束保存一条练习记录到 GameRecord 表，`practice_mode = "measure_loop"`，`measure_range` 记录选中范围
   - 小节缩略图上的历史准确率取最近 5 次练习的平均值
10. **最弱小节推荐**：
    - 游戏准备页显示「推荐练习」区域，自动列出准确率最低的 3 个小节
    - 点击推荐小节直接进入该小节的重复练习
    - 全曲未练习过时不显示推荐区域

**成功**
- 用户可选择任意单个小节或连续范围进行重复练习
- 循环次数可配置，默认无限循环
- 每次循环显示准确率及与上次对比
- 练习记录独立保存，不影响全曲进度
- 最弱小节自动推荐

**失败**
- 选择了 0 个小节 → 「开始练习」按钮置灰，提示"请至少选择 1 个小节"
- 乐谱解析失败无法生成小节缩略图 → 提示"乐谱解析失败，请重新导入"

**异常表现**
- 练习中切后台 → 同普通模式，暂停音频和游戏，恢复后从当前循环的当前小节开头重开
- 循环次数设为固定次数，达到后 → 显示最终结算页（含各次循环准确率趋势图），按钮「再练一轮」「退出」
- 用户在单次循环中退出 → 保存已完成部分的练习记录，不保存本次不完整循环
- 选中范围包含休止符小节 → 正常练习，休止符小节无台阶，节拍器继续

## 4. ADR 技术决策

> **技术选型替换规则**：以下 ADR 均为 **v1 推荐选型**，不是强制约束。开发 AI 或开发者可在满足以下全部条件的前提下替换为更优方案：
> 1. 替换后必须通过第 7 章全部验收项（尤其是准确性 KPI 和延迟 KPI）
> 2. 替换必须不违反第 5.1 节硬性规则（HR）
> 3. 替换需记录为新 ADR，说明替换原因、对比和验证结果
> 4. 核心目标（准确性、低延迟、离线、Android 7-16 兼容）不得因技术替换而降低
>
> **替换验证流程**：
> - 音高检测算法替换：必须在 MIR-1K / iKala 标准人声数据集上离线测试，统计准确率、八度错误率、颤音跟踪误差，与 v1 基准对比
> - 音频采集方案替换：必须在至少 3 款不同档次设备上实测端到端延迟 P50/P95，满足 HR-02
> - 存储方案替换：必须保证存档格式向后兼容，旧版本存档可正常读取；如不兼容需提供迁移脚本
> - 渲染方案替换：必须在中端机实测 60fps 稳定性，低端机 ≥30fps
>
> **回滚机制**：替换后若任一 KPI 不达标，必须回退到 v1 推荐方案，不得带着不达标指标发布。
>
> **存档兼容性**：任何技术替换不得破坏已有的用户存档数据（乐谱库、进度、设置）。数据模型变更需提供版本号和迁移逻辑。

---

### ADR-001：跨平台应用框架

| 方案 | 优势 | 劣势 |
|---|---|---|
| **Flutter（推荐）** | 单一代码库 Dart，FFI 直接调用 C 库（aubio/Oboe），Skia 渲染 60fps 有保障，热重载提升开发效率 | iOS 需后续适配 Metal；音频需原生插件 |
| React Native | JS 生态丰富 | JS Bridge 引入 100ms+ 延迟，无法满足实时音高检测；音频需原生模块 |
| Kotlin 原生 | 性能最优，Android  API 直接访问 | 仅 Android，开发成本高，aubio 需 JNI 封装，未来跨平台需重写 |

**推荐选型（v1 默认）：Flutter**  
**放弃原因**：React Native 的 JS 桥接延迟不可接受；Kotlin 原生锁定单平台且与 FFI 方案冲突。

---

### ADR-002：音高检测算法与库

| 方案 | 优势 | 劣势 |
|---|---|---|
| **aubio + YIN（推荐）** | C 库性能高，YIN 对单声部人声基频检测准确，支持置信度输出，FFI 直接调用，Singscope 同类方案 | 需交叉编译 Android .so，八度错误需后处理修正 |
| TarsosDSP | Java 实现，集成简单 | JVM GC 导致检测抖动，延迟高，不适合实时 |
| 自实现 FFT + 自相关 | 完全可控 | 开发周期长，难以达到 aubio 的鲁棒性 |
| Google ML Kit 数字音频 | 端侧 ML | 无专用人声基频检测 API，过度封装 |
| fcomb（aubio 内备选） | 对高频更敏感 | 对男低音易漏检，作为 YIN 失败时的 fallback |

**推荐选型（v1 默认）：aubio YIN 为主检测器，fcomb 为备选**  
**放弃原因**：TarsosDSP 延迟与 GC 问题；自实现重复造轮子；ML Kit 无匹配能力。

---

### ADR-003：低延迟音频采集

| 方案 | 优势 | 劣势 |
|---|---|---|
| **Oboe（推荐）** | Google 官方推荐，AAudio 低延迟路径，自动回退 OpenSL ES，C++ 与 aubio 同语言无缝衔接 | 需编写 C++ 插件代码 |
| AudioRecord (Java) | API 简单 | 经 JVM 传递音频数据，GC 停顿，延迟 >100ms |
| OpenSL ES 直接 | 广泛兼容 | 已被 AAudio 取代，API 复杂，部分设备有 bug |

**推荐选型（v1 默认）：Oboe**  
**放弃原因**：AudioRecord 延迟不达标；OpenSL ES 已过时且 Oboe 已封装其回退路径。

---

### ADR-004：乐谱输入格式

| 方案 | 优势 | 劣势 |
|---|---|---|
| **MusicXML（推荐）** | 行业标准，包含音高、时值、调号、拍号、速度完整信息，.mxl 压缩体积小 | 解析需处理 XML 复杂度，变体多 |
| MIDI | 文件小，时序精确 | 缺乏等音异名拼写、调号、演奏法信息；无法区分升 C 与降 D |
| ABC 记谱 | 文本格式，易解析 | 流行度低，复杂乐谱表达能力弱 |
| 图片 OCR | 用户可直接拍照 | 识别准确率不足，错误率高，v1 不可靠 |

**推荐选型（v1 默认）：MusicXML（.xml / .mxl）**  
**放弃原因**：MIDI 丢失记谱语义；ABC 生态小；OCR 准确率无法保证音准训练的基础正确性。

---

### ADR-005：游戏渲染方案

| 方案 | 优势 | 劣势 |
|---|---|---|
| **Flutter CustomPainter + Ticker（推荐）** | 完全控制渲染管线，与 Flutter Widget 生态无缝集成，音高可视化叠加层易于实现，包体积小 | 需自行实现以下模块：①游戏循环（Ticker + dt 计算）②相机滚动（地图平移）③矩形碰撞检测（角色 vs 台阶）④粒子/特效系统 ⑤坐标变换（音高↔像素） |
| Flame 引擎 | Flutter 原生 2D 游戏引擎，内置游戏循环、碰撞、相机、粒子 | 对本 App 而言物理/碰撞需求简单，引入引擎增加抽象层；音高曲线等自定义绘制仍需 CustomPainter；包体积增加 ~2MB |
| Unity | 成熟游戏引擎，特效丰富 | 包体积巨大（>100MB），与 Flutter 集成复杂，过度设计 |

**推荐选型（v1 默认）：CustomPainter + Ticker 自定义游戏循环**

**放弃原因**：Flame 对本场景收益有限且增加依赖；Unity 过重且与 Flutter 技术栈冲突。

**自实现模块清单与风险**：
| 模块 | 实现复杂度 | 风险 | 缓解措施 |
|---|---|---|---|
| 游戏循环 | 低 | Ticker 后台暂停需手动处理 | 监听 AppLifecycleState，paused 时停止 Ticker |
| 相机滚动 | 低 | 变速时滚动速度跳变 | 使用 dt 积分而非固定步长，变速时线性插值 |
| 碰撞检测 | 低 | 矩形重叠判定边界条件 | 角色用点判定（中心 Y），台阶用区间判定，避免边缘歧义 |
| 粒子/特效 | 中 | 粒子过多导致掉帧 | 粒子上限 50 个，低端机关闭 |
| 坐标变换 | 低 | 音高范围变化时台阶位置跳变 | 可视音域变化时使用动画过渡 |

**迁移条件**：若后续需要复杂物理（角色跳跃弧线）、多角色碰撞或丰富特效，评估迁移至 Flame。

---

### ADR-006：本地存储

| 方案 | 优势 | 劣势 |
|---|---|---|
| **SQLite (sqflite) + SharedPreferences（推荐）** | SQLite 支持关系查询、事务、乐谱库与进度一对多；SharedPreferences 适合简单设置 | 需编写表结构与迁移 |
| Hive (NoSQL) | 纯 Dart，速度快，无需 SQL | 复杂查询（如按准确率排序、小节状态统计）不便 |
| 仅 SharedPreferences | 极简 | 无法存储结构化乐谱地图与多小节进度 |

**推荐选型（v1 默认）：SQLite 存储乐谱地图、进度、统计；SharedPreferences 存储用户设置**  
**放弃原因**：Hive 查询能力不足；纯 KV 无法表达小节级进度。

### ADR-007：状态管理

| 方案 | 优势 | 劣势 |
|---|---|---|
| **Riverpod（推荐）** | 编译期安全，无需 BuildContext，支持异步 Provider，适合音频流 + 游戏状态的复杂组合 | 学习曲线略陡 |
| Provider | 简单 | 依赖 context，嵌套地狱，异步支持弱 |
| Bloc | 事件驱动清晰 | 模板代码多，对实时音频流过度设计 |

**推荐选型（v1 默认）：Riverpod**  
**放弃原因**：Provider 异步能力不足；Bloc 模板过重。

### ADR-008：架构分层与 UI 解耦

| 方案 | 优势 | 劣势 |
|---|---|---|
| **Clean Architecture 三层分离（推荐）** | Domain 层纯 Dart 无 Flutter 依赖，UI 可整体替换，业务逻辑可单元测试，接口明确 | 初期代码量略多，需严格遵守依赖方向 |
| MVVM（ViewModel+View） | 简单直接，Flutter 社区常见 | ViewModel 仍可能依赖 BuildContext，UI 替换成本高 |
| 传统分层（Model-View-Controller） | 最简单 | Controller 容易膨胀，业务与 UI 混杂 |

**推荐选型（v1 默认）：Clean Architecture 三层分离**

**放弃原因**：MVVM 的 ViewModel 易耦合 Flutter；MVC 无法保证业务逻辑独立。本 App 音高检测、命中判定、存档等核心逻辑需长期稳定，UI 可能迭代（如换皮肤、换渲染引擎），必须彻底解耦。

**分层定义与依赖方向**：
```
Presentation (UI)  ──implements──▶  Domain Interfaces
        │                                    ▲
        │                                    │
        ▼                                    │
  Riverpod Providers  ──calls──▶  Domain UseCases
                                          ▲
                                          │
                              Data Repositories ──implements──▶  Domain Repositories
```

**强制规则（v1 推荐架构下）**：
1. Domain 层（`lib/domain/`）与 UI 框架解耦，可独立运行单元测试
2. Domain 层定义所有接口（abstract class），Presentation 和 Data 层实现
3. Presentation 层（`lib/presentation/`）只负责渲染和用户交互，不包含任何业务逻辑
4. 业务逻辑变更只需修改 Domain 层，UI 变更只需修改 Presentation 层，互不影响
5. 依赖注入统一在 `lib/app.dart` 或 `lib/main.dart` 完成，各层不直接 new 依赖

> 注：以上为 v1 推荐的 Clean Architecture 实现约束。若采用其他解耦架构（如 MVVM、MVI），需满足 HR-12 业务逻辑与 UI 解耦的核心原则。

## 5. 历史约束 & BUG 禁止复现清单

### 5.1 硬性规则（不得违反）

> 以下规则为产品核心约束，任何技术选型或实现方案都不得违反。违反即视为不达标。

| 编号 | 规则 | 原因 |
|---|---|---|
| HR-01 | 音高检测必须保留**浮点 MIDI**，禁止四舍五入为整数或自动修正到最近半音 | 用户需要看到真实偏差，自动纠错会掩盖音准问题 |
| HR-02 | 端到端音频延迟 < 100ms（P50），< 150ms（P95） | 超过 150ms 用户会明显感觉不跟手，无法准确唱准 |
| HR-03 | 台阶坐标系统：**屏幕顶部 = 高频，屏幕底部 = 低频** | 用户明确指定，不得改为"上低下高" |
| HR-04 | 一个台阶 = 一个半音（1 MIDI 编号），逻辑像素（dp）高度固定 | 保证音高距离的视觉一致性，不受屏幕密度影响 |
| HR-05 | 以小节为最小存档单位，小节边界必须存档 | 用户明确要求 |
| HR-06 | 必须区分男声/女声，提供八度偏移（男声默认 -12 半音） | 男女天然音高差约八度，不处理则男声用户永远唱不准 |
| HR-07 | 练习模式默认开启 | 新用户友好，用户明确要求 |
| HR-08 | 所有音频处理在本地完成，不上传任何录音数据，不申请 INTERNET 权限 | 隐私 + 离线需求 |
| HR-09 | 存档写入必须保证原子性（事务或等效机制），防止崩溃导致存档损坏 | 数据完整性 |
| HR-10 | 人声检测准确率 ≥ 92%（标准数据集，偏差 <50 音分），八度错误率 < 2% | 准确性是本 App 的核心竞争力，对标 Singscope |
| HR-11 | 标准音 440Hz 检测准确率 ≥ 99% | 基础准确性保障 |
| HR-12 | 业务逻辑必须与 UI 视图解耦，UI 可整体替换而不影响核心逻辑 | 架构原则，保证长期可维护性 |
| HR-13 | 支持 Android 7.0（API 24）~ Android 16（API 36） | 用户明确要求 |
| HR-14 | 完全离线运行，无网络时所有功能正常 | 用户明确要求 |
| HR-15 | 判定层必须使用质量加权音高，低质量帧（置信度<0.5）不得直接导致 miss | 检测不稳定时直接判 miss 会让用户觉得"永远唱不准"，损害练习体验 |
| HR-16 | 显示用音高与判定用音高必须分离：显示原始浮点 MIDI，判定用质量加权值 | 既保证用户看到真实偏差（HR-01），又保证判定公平 |

| REC-06 | 应用框架使用 Flutter + Dart | 可替换为其他跨平台或原生方案，但必须满足 HR-13 兼容性和 HR-02 延迟 |
| REC-07 | 架构使用 Clean Architecture 三层分离 | 可替换为其他解耦架构，但必须满足 HR-12 业务逻辑与 UI 解耦 |
| REC-08 | 本地存储使用 SQLite + SharedPreferences | 可替换为其他本地存储方案，但必须满足 HR-09 原子性 |
| REC-09 | 游戏渲染使用 Flutter CustomPainter + Ticker | 可替换为 Flame、Unity 等渲染方案，但必须满足 60fps 性能 KPI |
| REC-10 | 状态管理使用 Riverpod | 可替换为其他状态管理方案 |

### 5.2 潜在问题与 BUG 禁止复现清单

| 编号 | 潜在问题 / BUG | 触发场景 | 禁止复现要求 | 应对措施 |
|---|---|---|---|---|

| BUG-22 | **44.1kHz 设备检测率不达标**：hop 512@44100 = 86.3Hz，若 NFR 要求 ≥90Hz 则不达标 | 仅支持 44.1kHz 的低端设备 | 检测率不得低于 85Hz，必须按采样率分别规定 | NFR 按采样率区分：48kHz ≥90Hz，44.1kHz ≥85Hz |
| BUG-23 | **练习模式容差过宽失去练习意义**：±100 音分 = ±1 半音，C 和 C# 都算"准" | 初学者使用练习模式 | 练习模式容差不得 >±75 音分 | 练习模式默认 ±75 音分，简单难度 ±100 仅作为入门过渡 |
| BUG-24 | **竖屏可视区域不足导致来不及准备**：竖屏宽度有限，若显示未来音符 <2 秒，用户无法及时反应 | 小屏手机、快速曲目 | 可视区域必须 ≥ 未来 4 秒乐谱 | 水平像素密度按屏幕宽度自适应，保证 4 秒窗口，台阶最小宽度 12dp |
| BUG-25 | **持续静音时游戏空转消耗资源**：用户不唱时角色不动但游戏循环和音频采集仍在运行 | 用户暂停唱歌、看手机 | 持续静音 >30 秒必须提示暂停，不得无限空转 | 5 秒提示，30 秒弹出暂停确认对话框 |
| BUG-26 | **节拍器与滚动速度不同步**：BPM 变化时节拍器声音和角色滚动速度脱节 | 含变速标记的乐谱 | 节拍器 BPM 必须与滚动速度严格同步 | 滚动速度和节拍器共用同一个 BPM 状态源，变速时同时更新 |
| BUG-27 | **八度错误率过高**：单算法在男声低音区八度错误率可达 8%，用户唱 C3 被识别为 C4 | 男低音演唱、嗓音沙哑 | 八度错误率必须 < 2%（HR-10），无论采用何种检测算法 | v1 推荐 YIN + fcomb 双算法融合；可替换为 CREPE 等更优算法，但必须通过八度错误率 KPI 验收 |
| BUG-28 | **前端处理缺失导致噪音误判**：无噪音抑制时，空调/风声被检测为随机音高 | 嘈杂环境、户外练习 | 静音段不得产生虚假音高，环境噪音 >60dB 时必须提示用户 | v1 推荐 70Hz 高通滤波 + 谱减法噪音抑制 + 自适应能量阈值；可替换为更优前端处理，但必须通过 AC-70 环境噪音鲁棒性验收 |
| BUG-29 | **音量差异导致检测失败**：用户音量小时检测不到，音量大时削波误判 | 不同用户、不同距离麦克风 | 40–90dB SPL 范围内准确率 ≥90%（AC-71） | v1 推荐 AGC 自动增益归一化 + 削波检测标记不可靠帧；可替换为更优音量自适应方案 |
| BUG-30 | **颤音被过度平滑**：α=0.3 平滑将颤音抹平，用户唱颤音时音高线变成直线 | 有颤音技巧的用户 | 颤音期间必须保留 ±20–40 音分自然波动 | 颤音检测（5–8Hz，±20–40 音分）后自动降低平滑系数至 α=0.1 |
| BUG-31 | **辅音起音误判为 miss**：b/p/d/t 等辅音起音瞬间音高检测输出异常值，导致音符起始即 miss | 所有用户演唱 | 起音前 2 帧不参与判定 | 音符起始后 2 帧（~21ms）保护期，允许不稳定 |
| BUG-32 | **蓝牙麦克风压缩导致音高偏移**：蓝牙 SBC 编码压缩影响低频基频检测，准确率下降 10%+ | 用户使用蓝牙耳机 | 默认不使用蓝牙麦克风，用户可手动开启 | 检测到蓝牙音频设备时提示"建议使用有线耳机或内置麦克风"，默认禁用蓝牙麦 |
| BUG-33 | **小节练习污染全曲进度**：小节练习模式的命中记录被误写入全曲 MeasureProgress，导致用户未唱完全曲却显示已通过 | 开发时共用存档逻辑 | 小节练习必须独立存档，不得更新全曲位置存档和完成存档 | GameRecord 表 practice_mode 字段区分，写存档时判断模式，measure_loop 模式跳过 PositionSave/MeasureProgress 写入 |
| BUG-34 | **循环间隔过短导致来不及准备**：每次循环结束后立即开始下一次，用户无法换气或调整 | 固定循环次数练习 | 循环间隔必须 ≥2 秒，显示本次结算后自动开始 | 循环结束后显示 2 秒结算浮层，然后 3 秒倒计时再开始下一次 |
| BUG-35 | **不连续小节选择导致地图断裂**：用户选择第 1、3、5 小节（不连续），地图生成时中间出现空白或时序错误 | 用户尝试多选不连续小节 | v1 禁止不连续多选，仅支持单个或连续范围 | 选择逻辑限制：选中新小节时若与已选范围不连续则清除之前选择，仅保留最新选择；UI 上明确提示"仅支持连续小节范围" |
| BUG-36 | **业务逻辑与 UI 耦合**：在 UI 层直接写命中判定/音高检测等业务逻辑，或业务逻辑直接操作 Widget，导致后续 UI 改版时业务逻辑需同步修改 | 开发时图省事跨层调用 | 业务逻辑必须与 UI 解耦，UI 变更不影响核心业务逻辑 | 架构审查：命中判定/音高检测/存档逻辑必须在业务逻辑层，UI 仅通过接口或回调接收状态；CI 可检查业务逻辑层不 import UI 框架 |
| BUG-37 | **低质量帧直接判 miss**：检测置信度低时（如环境噪音、起音瞬间）直接用原始音高判定，导致用户明明唱准了却被判 miss | 嘈杂环境、辅音起音、用户距离麦克风较远 | 低质量帧（置信度<0.5）不得直接导致 miss，必须使用质量加权判定 | 判定层使用 Q 值加权平均，低质量帧降低权重，不可用帧跳过判定 |
| BUG-38 | **显示与判定混用同一音高**：显示用平滑后的音高，用户看不到真实偏差；或判定用原始音高，波动导致误判 | 开发时图省事只用一个音高数据源 | 显示用原始浮点 MIDI，判定用质量加权值，必须分离 | 代码审查：渲染层和判定层使用不同的 Stream 或字段 |
| BUG-39 | **质量监控缺失导致用户不知情**：检测质量差时用户不知道，继续唱却全是 miss，误以为自己音准差 | 环境嘈杂、麦克风被遮挡、蓝牙麦压缩 | 必须实时显示质量指示器，低质量时主动提示用户 | 屏幕角落绿/黄/红指示器，低质量时文字提示 |
| BUG-40 | **为减包体积牺牲核心体验**：为了 APK 更小而简化音高检测算法、降低采样率、删除核心功能或降低渲染质量 | 开发时追求小体积 | 不得因体积优化降低准确性、延迟、帧率或删除核心功能 | 体积优化后必须重新跑全部验收项，对比优化前后无性能下降和功能缺失 |

### 6.1.1 音高识别准确性 KPI（核心指标）

| 指标 | 要求 | 测量方式 |
|---|---|---|
| 标准音检测准确率 | ≥ 99%（440Hz 正弦波，偏差 <10 音分算正确） | 播放 440Hz 测试 1000 帧统计 |
| 人声基频检测准确率 | ≥ 92%（标准人声数据集，偏差 <50 音分算正确） | 使用 MIR-1K / iKala 等人声数据集离线测试 |
| 八度错误率 | < 2%（检测结果与真实音高差 ≥12 半音算错误） | 标准人声数据集统计八度跳变错误次数 |
| 浊音判定准确率 | ≥ 95%（有声音/无声音分类正确） | 标注数据集对比 |
| 男声低音区准确率 | ≥ 88%（80–180Hz，偏差 <50 音分） | 男声数据集专项测试 |
| 女声高音区准确率 | ≥ 90%（200–600Hz，偏差 <50 音分） | 女声数据集专项测试 |
| 颤音跟踪误差 | < 15 音分（颤音期间检测值与真实值的平均偏差） | 合成颤音信号测试 |
| 起音响应延迟 | < 50ms（从发声到检测出稳定音高的时间） | 高速摄像 + 音频同步测量 |
| 环境噪音鲁棒性 | SNR ≥ 10dB 时准确率下降 <5% | 在 50dB/60dB/70dB 白噪音环境下测试 |
| 音量适应性 | 40dB–90dB SPL 范围内准确率 ≥90% | 不同音量播放标准音测试 |

### 6.1.2 判定层准确性 KPI（质量加权后）

> 检测层准确率衡量"音高检测对不对"，判定层准确率衡量"用户唱准时系统是否判对"。低质量帧的容错处理直接影响用户体验。

| 指标 | 要求 | 测量方式 |
|---|---|---|
| 唱准时判 hit 率 | ≥ 95%（用户实际唱准（偏差<50音分）时，系统判定为 hit 的比例） | 标准人声数据集模拟判定流程，统计唱准帧被判 hit 的比例 |
| 唱不准时判 miss 率 | ≥ 90%（用户实际唱不准（偏差>75音分）时，系统判定为 miss 的比例） | 合成偏移音高信号测试 |
| 低质量帧误判率 | < 3%（置信度<0.5的帧直接导致 miss 的比例） | 统计低质量帧在判定中的权重和影响 |
| 连续演唱判定准确率 | ≥ 90%（连续 10 个音符以上的乐句，整体判定与人工标注一致率） | 完整曲目人工标注对比 |
| 起音阶段误判率 | < 5%（音符起始后前 100ms 内的误判比例） | 起音保护期效果验证 |

### 6.5.1 APK 体积优化原则

> **核心原则**：在保证体验的前提下尽量小，**不得为了减小体积而牺牲核心体验**。体积优化是"锦上添花"，不是"必须达标"。

**不得因体积优化而牺牲的体验（硬约束）：**
- 音高检测准确性（HR-10/HR-11，不得简化算法或降低采样率）
- 端到端延迟（HR-02，不得增大 buffer/hop 换取体积）
- 游戏渲染帧率（≥60fps 中端机，不得简化渲染）
- 功能完整性（不得删除新手教程、结算页面、小节练习等核心功能）
- 音频质量（不得降低采样率或压缩音频处理精度）

**推荐优化方向（不影响体验）：**
1. **代码混淆与压缩**：启用 R8/ProGuard 代码混淆和优化
2. **资源压缩**：图片资源使用 WebP 格式，移除未使用资源
3. **ABI 拆分**：按 arm64-v8a / armeabi-v7a 分别构建，用户下载对应架构
4. **原生库优化**：aubio/Oboe 仅编译必要模块，使用 `-Os` 优化体积
5. **字体子集化**：仅打包使用到的字符，不打包完整字体
6. **按需加载**：大资源（如示例乐谱）不打包进 APK，首次启动后下载或用户手动导入

**体积预算分配（v1 参考）：**
| 组成部分 | 预估体积 | 说明 |
|---|---|---|
| Flutter 引擎 | ~15MB | 不可避免 |
| 原生库（aubio + Oboe） | ~3-5MB | C/C++ 编译产物 |
| 应用代码 | ~2-3MB | Dart 代码 AOT 编译 |
| 资源（图片/字体/音效） | ~3-5MB | 可压缩优化 |
| 其他 | ~2MB | Android 框架、清单等 |
| **合计** | **~25-30MB** | 远低于 50MB 目标 |

**验收标准：**
-  arm64-v8a 单架构 APK < 50MB
- 全架构通用 APK < 80MB（如不拆分 ABI）
- 体积优化后必须通过全部功能和性能验收项，不得有功能缺失或性能下降

### 6.6 可访问性（基础）

- 文字最小 12sp，关键信息 ≥ 14sp
- 颜色不仅依赖红绿区分（台阶音高分组同时用图案/形状辅助）
- 支持系统字体缩放（游戏内固定字号，菜单页跟随系统）
- 文本对比度 ≥ WCAG AA 标准（正文 4.5:1，大字 3:1）
- 支持 TalkBack 屏幕阅读器：菜单页所有可交互元素提供 contentDescription
- 命中/miss 提供触觉反馈（振动），不依赖视觉：命中短震 10ms，miss 长震 30ms
- 支持系统高对比度模式：游戏内台阶边框加粗，角色轮廓增强
- 支持"减少动态效果"系统设置：开启后粒子特效降级为静态高亮
- 游戏内关键操作（暂停、返回）提供大尺寸触控目标（≥48dp）
- 色弱友好：偏差反馈同时使用颜色（红/绿）+ 方向箭头（↑/↓）+ 文字（偏高/偏低）

## 8. 完整用户操作流程

### 8.1 首次启动与初始化流程

```
用户点击 App 图标
  → 启动页（< 3s）
  → 权限引导页（说明麦克风用途："用于实时检测您的音高以控制游戏角色"）
      → 用户点击"开始授权"
      → 系统弹出 RECORD_AUDIO 权限对话框
          → [允许] → 进入声线选择页
          → [拒绝] → 显示"需要麦克风权限才能进行音准训练"
              → [再次尝试] → 重新弹权限
              → [永久拒绝] → 显示"请在系统设置中开启麦克风权限" + 前往设置按钮
  → 声线选择页（男声 / 女声）
      → 选择后保存到 SharedPreferences，应用默认八度偏移
  → （可选）音域校准引导页
      → [开始校准] → 唱"啊"3秒 → 计算偏移 → 预览确认
      → [跳过] → 使用默认偏移
  → 新手教程页（仅首次启动显示，可在设置中重新打开）
      → Step 1：玩法说明 — "对着麦克风唱歌，角色会随音高上下移动"
      → Step 2：坐标说明 — "屏幕上方是高音，下方是低音，每个台阶是一个音"
      → Step 3：实操练习 — 显示 3 个目标台阶，引导用户依次唱出对应音高，角色移动到台阶上即通过
      → Step 4：节奏说明 — "跟着节拍器，角色到达台阶时唱准对应音高"
      → [开始体验] → 进入一首内置示例曲目的第一小节试玩
      → [跳过教程] → 直接进入首页
  → 首页（曲库列表，空状态提示"导入乐谱开始练习"，附带"试玩示例曲"按钮）
```

### 8.2 正常游戏流程

```
首页 → 点击"导入乐谱"
  → 系统文件选择器
  → 选择 .xml/.mxl 文件
  → 解析中（loading）
  → [成功] 曲库出现新曲目 → 点击曲目
  → 游戏准备页（显示曲目信息、最弱小节推荐、设置快捷入口、「开始」按钮、「选择小节练习」按钮）
  → [全曲模式] 点击"开始"
      → 竖屏进入游戏
      → 3 秒倒计时（同时初始化音频流，节拍器预响 2 小节）
      → 音频流打开成功 → 倒计时结束 → 节拍器启动 → 游戏开始
      → 角色固定在屏幕左侧 30% 位置，地图向左滚动
      → 第一个音符到达角色位置前 1 秒显示"准备"提示
      → 音符到达角色位置时显示"唱"提示
      → 用户演唱 → 音高实时检测 → 角色垂直移动 → 台阶命中/miss
      → 小节边界 → 结算 → 自动存档 → 继续下一小节
      → 全曲结束 → 停止滚动与音频 → 结算页（总准确率、评级 S/A/B/C/D、偏差热力图、各小节统计）
      → [再唱一次] / [返回曲库] / [查看详情→点击小节进入重复练习]
  → [小节练习模式] 点击"选择小节练习"
      → 小节选择界面（横向滚动小节缩略图，显示序号/音符概览/历史准确率/通过状态）
      → 单击选中单个小节，或长按拖动框选连续范围
      → [未选中] 「开始练习」按钮置灰
      → [已选中] 显示"第 X–Y 小节" → 点击「开始练习」
      → 设置循环次数（默认无限循环）→ 进入游戏
      → 仅加载选中小节的地图
      → 3 秒倒计时 → 节拍器预响 → 开始
      → 选中小节依次滚动 → 演唱 → 命中/miss
      → 选中范围结束 → 停止滚动 → 显示本次循环结算 2 秒（准确率、与上次对比↑↓—）
      → [未达设定次数] 自动 3 秒倒计时 → 开始下一次循环
      → [达到设定次数/用户退出] → 最终结算页（各次循环准确率趋势图）
      → [再练一轮] / [退出到曲库]
      → 注意：小节练习不更新全曲位置存档和完成存档
```

### 8.3 系统权限异常流程

**麦克风权限被拒（首次）**
```
游戏准备页点击"开始"
  → 检测到无麦克风权限
  → 弹出权限说明对话框
  → [去授权] → 系统权限对话框
      → [允许] → 继续游戏
      → [拒绝] → 返回准备页，显示"麦克风权限未开启"
```

**麦克风权限永久拒绝**
```
检测到 shouldShowRequestPermissionRationale = false 且权限未授予
  → 显示永久拒绝引导页："麦克风权限已被永久拒绝"
  → [前往设置] → 打开系统 App 详情设置页
  → 用户手动开启后返回 App → onResume 检测权限已授予 → 可开始游戏
```

**存储权限被拒**
```
点击"导入乐谱"
  → 检测到无存储权限（API <33）
  → 申请权限
  → [拒绝] → Toast"需要存储权限以选择乐谱文件"，仍可使用其他功能
  → （API 33+ 使用系统文件选择器，无需存储权限）
```

**麦克风权限运行时被撤销**
```
游戏中 / 准备页 → 用户切到系统设置 → 手动关闭麦克风权限 → 返回 App
  → onResume 检测权限已从 granted 变为 denied
  → 系统行为：
      1. 立即停止并关闭 Oboe 音频流（防止 crash）
      2. 暂停游戏 Ticker，保存当前进度到内存
      3. 弹出对话框："麦克风权限已被关闭，无法继续音准训练"
      4. [前往设置] → 打开系统 App 详情设置页
      5. [返回曲库] → 触发位置存档，退出到曲库
  → 用户在设置中重新开启权限 → 返回 App → onResume 检测权限已恢复
      → 显示"权限已恢复"，可重新开始游戏（当前内存进度可能已丢失，从最近存档点恢复）
```

**企业 MDM / 儿童模式禁用麦克风**
```
检测到麦克风权限已授予，但 Oboe 打开失败且错误码为权限被策略限制
  → 提示"麦克风被系统策略禁用，请联系设备管理员或退出儿童模式"
  → 不引导至普通权限设置页（无效）
```

### 8.4 切后台流程

**正常切后台与恢复**
```
游戏中 → 用户按 Home / 切换到其他 App
  → AppLifecycleState = inactive → paused
  → 系统行为：
      1. 游戏 Ticker 暂停（角色停止滚动）
      2. Oboe 音频流 stop（释放麦克风）
      3. 当前小节进度保存到内存（不触发小节结算）
      4. 屏幕显示"已暂停"遮罩 + [继续] 按钮
  → 用户返回 App
  → AppLifecycleState = resumed
  → 系统行为：
      1. 重新打开 Oboe 音频流（最多重试 3 次，间隔 500ms）
          → [成功] → 显示"继续"按钮，用户点击后从暂停点恢复
          → [失败（麦克风被占用）] → 显示"麦克风被占用"提示
      2. 游戏 Ticker 恢复
      3. 角色从暂停位置继续
```

**切后台后进程被系统杀死（内存回收）**
```
App 在后台停留时间过长（通常 >30 分钟，取决于设备内存）
  → 系统回收 App 进程以释放内存
  → 用户从最近任务列表或桌面图标重新进入 App
  → 检测到是冷启动（onCreate，而非 onResume）
  → 系统行为：
      1. 不尝试恢复内存中的游戏状态（已丢失）
      2. 读取 SQLite 中最近的位置存档（小节边界已存）
      3. 进入首页曲库，提示"上次游戏未正常结束，已恢复到第 X 小节"
      4. 用户点击曲目 → 从最近存档小节开始
  → 注意：若被杀时正处于小节中间（未到边界），该小节内的进度丢失，从该小节开头重唱
```

**小节结算瞬间切后台（存档写入中断）**
```
用户恰好在小节结算（SQLite 事务写入）的瞬间按 Home
  → AppLifecycleState = paused
  → 系统行为：
      1. 等待当前 SQLite 事务完成（最多 200ms，事务本身 <50ms）
      2. 若事务已提交 → 存档完整，正常暂停
      3. 若事务尚未开始 → 不触发结算，当前小节进度保存到内存，恢复后继续演唱
      4. 若事务写入失败（如低存储）→ 回滚事务，提示"存档失败"，该小节不标记完成
  → 禁止：在 paused 状态下启动新的 SQLite 写入
```

**倒计时期间切后台**
```
游戏开始前 3 秒倒计时进行中 → 用户切后台
  → 暂停倒计时，停止音频流初始化
  → 返回 App → 倒计时重置为 3 秒，重新开始（不保留之前的倒计时进度）
```

**分屏 / 多窗口模式**
```
用户进入分屏模式（Android 7.0+）
  → App 窗口尺寸变化，Flutter 自动重建布局
  → 游戏状态由 Riverpod 管理，不丢失
  → 若分屏后窗口宽度过小（<360dp）→ 提示"窗口过小可能影响游戏体验"
  → 音频流不受影响，继续采集
```

### 8.5 锁屏流程

**正常锁屏与解锁**
```
游戏中 → 用户按电源键锁屏 / 自动锁屏
  → AppLifecycleState = detached → paused
  → 同切后台：暂停游戏 + 停止音频 + 显示暂停遮罩
  → 解锁屏幕 → AppLifecycleState = resumed
  → 同切后台恢复流程
  → 注意：若锁屏时间过长（>5 分钟），系统可能回收音频资源，恢复时需完整重新初始化音频流
```

**锁屏期间二次中断（闹钟 / 来电 / 提醒）**
```
锁屏状态下 → 闹钟响铃 / 来电 / 日历提醒触发
  → 系统唤醒屏幕并播放提示音，可能再次抢占音频焦点
  → App 仍处于 paused 状态，不做额外处理（音频流已停止）
  → 用户处理完闹钟/来电后解锁屏幕
  → AppLifecycleState = resumed → 同正常恢复流程
  → 若闹钟触发时 App 进程已被系统回收 → 走"切后台进程被杀死"流程
```

**智能解锁失败 / 生物识别多次失败**
```
锁屏后用户尝试指纹/人脸解锁失败多次
  → 系统要求输入 PIN/密码
  → App 仍处于 paused，不影响
  → 成功解锁后正常恢复
```

### 8.6 麦克风被占用流程

**游戏开始时被占用**
```
点击"开始" → Oboe 打开音频流
  → 返回错误（ErrorDisconnected / 设备被其他客户端占用）
  → 系统行为：
      1. 显示对话框："麦克风被其他应用占用，请关闭通话、录音或语音助手后重试"
      2. [重试] → 重新尝试打开音频流
      3. [返回] → 回到准备页
  → 用户关闭占用应用后 → [重试] → 成功 → 开始游戏
```

**游戏中被抢占（如来电）**
```
游戏中 → 来电接入 / 其他 App 抢占麦克风
  → 音频采集错误回调触发（输入流断开）
  → 系统行为：
      1. 立即暂停游戏 Ticker
      2. 停止并关闭当前音频流
      3. 保存当前进度到内存
      4. 显示"音频中断"遮罩
  → 通话结束 / 麦克风释放后
  → 用户返回 App → onResume
  → 自动尝试重新打开音频流（延迟 1 秒，避免与系统释放竞争）
      → [成功] → [继续] 按钮恢复
      → [失败] → 提示仍被占用
```

**语音助手激活（Google Assistant / 小爱同学等）**
```
游戏中 → 用户说"Hey Google" / 长按 Home 键 / 手势激活语音助手
  → 语音助手抢占麦克风输入
  → 音频采集错误回调触发（输入流断开）或输入数据突然变为静音
  → 系统行为：
      1. 暂停游戏 + 停止音频流
      2. 显示"音频中断"遮罩，提示"语音助手已激活"
  → 用户退出语音助手 → 返回 App
  → onResume → 自动重试打开音频流 → 恢复游戏
```

**屏幕录制 / 投屏占用麦克风**
```
游戏中 → 用户开启屏幕录制并选择"录制麦克风音频"，或开启投屏共享音频
  → 麦克风被录制/投屏应用独占
  → Oboe 打开失败或输入静音
  → 系统行为：
      1. 暂停游戏
      2. 提示"麦克风被屏幕录制/投屏占用，请关闭后继续"
      3. [重试] → 重新打开音频流
  → 用户停止录制/投屏 → [重试] → 成功 → 恢复
```

### 8.7 来电与通知中断流程

```
游戏中 → 来电（电话/微信语音）
  → 系统自动暂停 App（同切后台流程）
  → 通话结束 → App 恢复 → 同切后台恢复流程
  → 若用户在通话中挂断并直接返回 → 自动恢复

游戏中 → 顶部横幅通知（短信/消息）
  → 不暂停游戏（Android 通知不抢占音频焦点时）
  → 若通知附带声音且系统降低游戏音量 → 不影响音高检测（检测的是麦克风输入，非输出）
  → 若用户下拉通知栏 → AppLifecycleState = inactive → 暂停
```

### 8.8 存档恢复流程

```
App 启动 → 首页曲库
  → 用户点击已有曲目（含进度）
  → 读取 SQLite 存档：
      → 存在有效存档（已通过小节数 > 0）
          → 显示"继续上次进度（第 X 小节）" / "从头开始"
          → [继续] → 游戏从第 X 小节开头加载，角色定位到该小节起始位置
          → [从头开始] → 清除该曲目进度（需确认），从第 1 小节开始
      → 无有效存档 → 直接从第 1 小节开始
  → 存档校验：
      → 读取存档校验和 → 不匹配 → 回退到上一个有效存档点
      → 所有存档损坏 → 提示"存档损坏，已重置进度"，从头开始
```

### 8.9 游戏中暂停与恢复

```
游戏中 → 用户点击暂停按钮（或按返回键）
  → 暂停 Ticker + 停止音频流
  → 显示暂停菜单：[继续] [重新开始本小节] [返回曲库] [设置]
  → [继续] → 恢复音频 + Ticker，从暂停点继续
  → [重新开始本小节] → 角色回退到当前小节开头，清除本小节已命中记录
  → [返回曲库] → 触发位置存档（保存当前小节索引），退出游戏
  → [设置] → 打开设置面板（可调节容差、八度偏移，更改后下一小节生效）
```

### 8.10 硬件异常汇总表

| 麦克风物理遮挡 | 检测到能量极低但权限正常 | 持续 5 秒后提示"未检测到声音，请检查麦克风是否被遮挡" | 温和提示 |
| 切后台 | AppLifecycleState | 暂停游戏 + 释放音频 | 暂停遮罩 |

| 锁屏 | AppLifecycleState detached | 暂停游戏 + 释放音频 | 暂停遮罩 |
| 锁屏期间闹钟/来电 | 二次音频焦点变化 | 保持 paused，解锁后统一恢复 | 无额外感知 |
| 来电 | 音频焦点丢失 + Oboe 断开 | 暂停游戏，通话后自动恢复 | 暂停遮罩，恢复提示 |
| 低存储 | SQLite 写入失败 + StorageManager | 提示"存储空间不足"，暂停存档 | Toast 提示 |
| 低电量 (<15%) | BatteryManager | 可选降低渲染帧率到 30fps 省电，不影响判定 | 帧率略降（可选） |
| 省电模式 | PowerManager.isPowerSaveMode | 降低检测帧率到 ~60Hz，渲染到 30fps，保证判定不丢 | 检测精度略降，提示 |
| 设备过热 | 无直接 API，通过性能下降推断 | 不主动处理，记录日志 | — |
| 耳机插拔 | AudioManager 广播 | 不影响麦克风输入（仍用手机麦克风），若耳机带麦则切换输入源 | 无感知（自动切换） |

| 分屏/多窗口 | windowMetrics 变化 | 自动适配布局，状态不丢失；窗口过小时提示 | 布局自适应 |
| 倒计时期间切后台 | paused 时检测倒计时状态 | 倒计时重置为 3 秒，恢复后重新开始 | 倒计时重新开始 |

### 8.11 持续静音 / 不唱处理流程

**游戏中用户持续不唱（静音 > 5 秒）**
```
游戏中 → 检测到连续 5 秒 unvoiced（无有效音高）
  → 系统行为：
      1. 角色保持最后位置并逐渐变暗（透明度降至 50%）
      2. 屏幕显示温和提示："请对着麦克风唱歌，音高控制角色上下移动"
      3. 游戏继续滚动（不暂停），未到达的音符自动记为 miss
  → 用户开始演唱 → 提示消失，角色恢复正常
  → 持续静音 > 30 秒 → 弹出"是否暂停？"对话框
      → [暂停] → 进入暂停菜单
      → [继续] → 保持游戏继续
```

**用户唱的音高持续超出显示范围**
```
游戏中 → 检测到连续 3 秒音高超出可视音域（过高或过低）
  → 角色停在屏幕顶部或底部边缘
  → 边缘显示箭头提示："音偏高，试着唱低一点" 或 "音偏低，试着唱高一点"
  → 超出范围期间，若目标音符在可视范围内，自动记为 miss
  → 音高回到可视范围 → 箭头消失，角色恢复正常移动
```

**麦克风被手遮挡 / 输入音量过低**
```
游戏中 → 检测到 RMS 能量持续低于阈值但权限正常
  → 持续 5 秒后提示："未检测到声音，请检查麦克风是否被遮挡，或增大演唱音量"
  → 不暂停游戏，提示 3 秒后自动消失
  → 能量恢复正常 → 不显示提示
```

## 附录 B：音高检测后处理流水线参数（v1 推荐基准值，可在满足 KPI 前提下调优）

### B.1 主参数表（48kHz）

| 步骤 | 参数 | 值 | 说明 |
|---|---|---|---|
| 采样率 | sample_rate | 48000 Hz（优先） | 设备不支持时回退 44100 |
| YIN buffer | buf_size | 2048 samples | ~42.7ms 分析窗口 |
| YIN hop | hop_size | 512 samples | ~10.7ms 步长，~93.75Hz 检测率 |
| 置信度阈值 | confidence | 0.7 | 低于此值判定 unvoiced |
| 能量门限 | rms_threshold | 0.01 (归一化) | 低于此值判定静音 |
| 八度纠错 | octave_jump_ratio | 1.9 | 帧间频率比 >1.9 且落在 2x/0.5x 附近时触发修正 |
| 中值滤波 | median_window | 3 frames | 去除单点尖峰 |
| 平滑 | ema_alpha | 0.3 | 指数移动平均系数，引入延迟 ~7ms |
| 浮点 MIDI | — | 69 + 12×log2(f/440) | 保留全部小数 |

### B.2 44.1kHz 设备回退参数

| 参数 | 48kHz 值 | 44.1kHz 值 | 说明 |
|---|---|---|---|
| buf_size | 2048 | 2048 | ~46.4ms 分析窗口，保持不变以保证低频检测精度 |
| hop_size | 512 | 512 | ~11.6ms 步长，~86.3Hz 检测率（满足 NFR ≥85Hz） |
| 检测率 | ~93.75Hz | ~86.3Hz | 44.1kHz 下检测率略低，仍满足要求 |

### B.3 端到端延迟预算分解（48kHz，目标 <100ms P50）

> 以下为 v1 推荐实现（Oboe + aubio YIN/fcomb）的延迟预算参考。替换技术方案后需重新计算各环节延迟，确保总延迟满足 HR-02。

| 环节 | 延迟 | 说明 |
|---|---|---|
| Oboe 采集缓冲 | 5–30ms | 低延迟模式 burst size，取决于设备 |
| 前端处理（高通+NS+AGC） | <2ms | C++ 层实时处理，逐帧计算 |
| YIN 分析窗口 | 42.7ms | buffer 2048 的固有延迟 |
| fcomb 校验 | <1ms | 与 YIN 并行运行 |
| 中值滤波 | ~10.7ms | 3 帧窗口，1 帧延迟 |
| EMA 平滑 | ~7ms | α=0.3 的群延迟 |
| 渲染等待 | 0–16.7ms | 最多等一帧 |
| **合计 P50** | **~68–88ms** | 满足 <100ms 目标 |
| **合计 P95** | **~105–135ms** | 满足 <150ms 目标 |

### B.4 前端处理链参数

| 步骤 | 参数 | 值 | 说明 |
|---|---|---|---|
| 音频源 | input_source | VOICE_RECOGNITION | Android 针对人声优化的音频源 |
| 高通滤波 | highpass_cutoff | 70 Hz | 滤除低频环境噪音，不影响人声基频（男声最低 ~85Hz） |
| 高通滤波 | filter_order | 2 | 二阶 Butterworth |
| 噪音抑制 | ns_method | spectral_subtraction | 谱减法，抑制稳态噪音 |
| 噪音抑制 | ns_strength | adaptive (0.3–0.8) | 安静环境 0.3，嘈杂环境最高 0.8 |
| 自动增益 | agc_target | -16 dBFS | 归一化目标电平 |
| 自动增益 | agc_attack | 5 ms | 增益上升时间 |
| 自动增益 | agc_release | 50 ms | 增益下降时间 |
| 削波检测 | clipping_threshold | 0.98 (归一化) | 信号绝对值 >0.98 判定为削波 |
| 削波处理 | clipping_action | 降低置信度至 0.3 | 标记不可靠帧 |

### B.5 双算法融合参数

| 参数 | 值 | 说明 |
|---|---|---|
| 主算法 | YIN | 对中低频人声准确 |
| 校验算法 | fcomb | 对高频更敏感，辅助八度校验 |
| 融合权重（一致时） | YIN 0.7 + fcomb 0.3 | 两算法偏差 <50 音分时 |
| 不一致时置信度 | 降为 0.5 | 偏差 ≥50 音分时标记不确定 |
| 频率范围约束 | 70–1200 Hz | 覆盖人声 C2–C6（MIDI 36–96） |
| 融合后浊音阈值 | 0.5 | 低于此值判定 unvoiced |

### B.6 后处理增强参数

| 参数 | 值 | 说明 |
|---|---|---|
| 八度纠错触发比 | 1.9 | 帧间频率比 >1.9 且落在 2x/0.5x 附近 |
| 八度纠错连续性 | 连续 3 帧 | 单帧跳变视为尖峰丢弃 |
| 八度纠错后置信度 | 0.6 | 纠错后降低置信度 |
| 中值滤波窗口 | 3 帧 | 去除单点尖峰 |
| 正常平滑系数 | α=0.3 | 非颤音期 |
| 颤音平滑系数 | α=0.1 | 颤音期，保留自然波动 |
| 颤音检测频率范围 | 5–8 Hz | 典型人声颤音频率 |
| 颤音检测幅度范围 | ±20–40 音分 | 典型人声颤音幅度 |
| 起音保护帧数 | 2 帧（~21ms） | 音符起始后不参与判定 |

### B.7 环境自适应参数

| 参数 | 值 | 说明 |
|---|---|---|
| 噪音采样时长 | 2 秒 | 游戏开始前静默采样 |
| 浊音能量阈值范围 | 0.005–0.02 | 安静 0.005，嘈杂最高 0.02 |
| 噪音提示阈值 | >60 dB | 超过此值提示用户换环境 |
| 用户音域校准低音时长 | 3 秒 | 唱舒适低音 |
| 用户音域校准高音时长 | 3 秒 | 唱舒适高音 |
| 校准取稳定段比例 | 中间 60% | 去掉起音和尾音，取中间稳定段中位频率 |

### C.2 Domain 层 UI 接口定义

#### C.2.1 GameRenderer（游戏渲染接口）

```dart
abstract class GameRenderer {
  /// 渲染当前检测到的用户音高（浮点 MIDI）
  void renderPitch(double midiFloat);

  /// 渲染角色位置（x 为水平进度 0-1，y 为垂直音高位置）
  void renderCharacter(double x, double y);

  /// 渲染单个台阶（音符）
  void renderStep(StepView step);

  /// 渲染命中效果（音符序号、偏差音分）
  void renderHit(int noteIndex, int deviationCents);

  /// 渲染 miss 效果（音符序号、偏差方向）
  void renderMiss(int noteIndex, MissDirection direction);

  /// 渲染小节进度（当前小节序号、总小节数、本小节命中数/总数）
  void renderMeasureProgress(int currentMeasure, int totalMeasures,
      int hitInMeasure, int totalInMeasure);

  /// 渲染节拍器提示（当前拍、总拍）
  void renderMetronomeBeat(int currentBeat, int beatsPerMeasure);

  /// 渲染进唱提示（"准备"/"唱"）
  void renderSingPrompt(SingPromptType type);

  /// 清空画布（暂停/退出时调用）
  void clear();
}
```

#### C.2.2 AudioFeedback（音频/触觉反馈接口）

```dart
abstract class AudioFeedback {
  /// 播放命中音效
  void playHitSound();

  /// 播放 miss 音效
  void playMissSound();

  /// 播放节拍器滴答声
  void playMetronomeTick(bool isDownbeat);

  /// 振动反馈（命中短震、miss 长震）
  void vibrate(Duration duration);

  /// 播放倒计时提示音
  void playCountdownBeep(int secondsLeft);

  /// 停止所有音效
  void stopAll();
}
```

#### C.2.3 GameStateCallback（游戏状态回调接口，UI 实现）

```dart
abstract class GameStateCallback {
  /// 音高变化时调用（每帧 ~10ms）
  void onPitchChanged(double midiFloat, double confidence);

  /// 音符命中时调用
  void onNoteHit(NoteResult result);

  /// 音符 miss 时调用
  void onNoteMiss(NoteResult result);

  /// 小节完成时调用（含结算数据）
  void onMeasureComplete(MeasureResult result);

  /// 游戏暂停时调用
  void onGamePaused(PauseReason reason);

  /// 游戏恢复时调用
  void onGameResumed();

  /// 全曲完成时调用（含最终结果）
  void onGameComplete(GameResult result);

  /// 发生错误时调用（麦克风故障、权限丢失等）
  void onGameError(GameError error);
}
```

### C.3 各层职责边界

| 层 | 职责 | 禁止 |
|---|---|---|
| **Domain** | 业务规则、状态机、算法、接口定义 | import Flutter、直接操作 Widget、直接读写数据库 |
| **Data** | MusicXML 解析、SQLite/SP 读写、数据模型转换 | 包含业务逻辑、直接操作 UI |
| **Presentation** | Widget 渲染、用户交互、实现 Domain 接口 | 包含命中判定、音高检测、存档逻辑等业务规则 |
| **Services** | Oboe/aubio FFI 封装、平台通道 | 包含业务逻辑 |

### C.5 UI 替换验证标准

1. 新建 Presentation 层实现，重新实现 `GameRenderer`、`AudioFeedback`、`GameStateCallback`、`AppNavigation` 四个接口
